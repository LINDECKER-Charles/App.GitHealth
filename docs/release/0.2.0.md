# GitHealth `0.2.0`

This release turns a single table into a workspace: several baselines per repository, a
capture chosen and carried across every tab, a visualisation of the topology and the drift,
and an analysis that can be watched reference by reference while it runs. It also adds the
first feature that reaches a network — an assistant backed by an agent command line already
installed on the machine, opt-in per repository. It is a `0.x`: the public contract is not
frozen, and this version already breaks part of it.

## Highlights

- several comparison baselines per repository, measured side by side;
- a capture selector obeyed by every tab and carried in the URL;
- a "Visualisation" tab: topology map, activity register and drift since the previous capture;
- an analysis watched as it runs, with a `git · read only` console naming every command;
- an assistant panel answering questions about a capture, with consent stored per repository;
- the interface, the scripts and the workflows written in English, with 464 message ids;
- GitHealth's own icon in the macOS bundle, in place of the packager's default.

## Before installing

GitHealth never updates remote references. Run your usual Git commands deliberately if you
need a recent view of the forge. The Windows installer and the macOS archives and `.pkg` are
neither signed nor notarised: SmartScreen and Gatekeeper ask for explicit approval on first
launch.

Two things changed that an existing installation will notice. Assistant conversations are
kept in the local database, so they follow `GET /api/exports/database` and any copy of it;
**Policies → Assistant → Delete every conversation** empties that history before a backup
leaves the machine. And a repository that was saved before this version starts with no
assistant consent granted, so the panel asks once before the first question.

Read the [user guide](../USER_GUIDE.md), the
[troubleshooting guide](../TROUBLESHOOTING.md) and the
[known limitations](../KNOWN_LIMITATIONS.md) before running GitHealth on a sensitive
repository.

## Acceptance on real repositories

Run on macOS 26.6.2 against two private repositories, with
[`tests/Infrastructure/Invoke-RealRepositoryAcceptance.ps1`](../../tests/Infrastructure/Invoke-RealRepositoryAcceptance.ps1).
The versioned record is [`acceptance-0.2.0.json`](acceptance-0.2.0.json); it is anonymised,
and carries no repository name, no path, no author name and no address.

| | Repository 1 | Repository 2 |
|---|---:|---:|
| Commits | 4,432 | 1,021 |
| Tracked files | 3,581 | 417 |
| References | 94 | 112 |
| Branches analysed | 59 | 62 |
| Branches cross-checked against `git rev-list` | 5 | 5 |
| Duration | 2.4 s | 2.8 s |
| Repository unchanged afterwards | yes | yes |

Both repositories covered the three cases the recipe requires: merged, diverged and
inactive branches. The counters GitHealth reported were compared against
`git rev-list --left-right --count` on five branches of each; `git for-each-ref`, the index,
the worktree diff and the reflogs were captured before and after each run and compared. CSV
and SQLite exports were produced, the application was restarted, and the last successful
snapshot was found again.

That last comparison is the one that matters: it is the check behind the claim that
GitHealth only ever reads. It passed on both repositories.
